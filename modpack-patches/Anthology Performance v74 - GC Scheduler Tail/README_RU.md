# Anthology Performance v74 — GC / Scheduler Tail

Версия v74 направлена на периодические «тики» при уже выросшем среднем FPS.
Она не снижает качество графики, дальность, частоту логики аддонов или число NPC.
Новая игра и очистка кэша шейдеров не нужны.

## Что показал контрольный лог v73

- Бинарник v73 действительно работал: в логе есть новая разбивка
  `[mt-frame/profile] game-breakdown`.
- Максимумы Lua GC повторялись в диапазоне примерно 105–242 мс и совпадали с
  пиками GameThread. За 300 кадров выполнялось около 1650–1714 шагов GC — почти
  шесть вызовов в каждом кадре.
- `seqParallel` периодически занимал до 152 мс, а отдельные проходы scheduler —
  примерно 69–96 мс. Среднее время рендера при этом уже было заметно ниже.
- Отдельный Lua-патч v73 не запускался: долго открытый Mod Organizer восстановил
  свой список модов без записи v73. Поэтому старый callback снова дважды сделал
  полный `collectgarbage("collect")` и сброс LuaJIT после загрузки.

## Что изменено

- Пошаговый Lua GC больше не копит восьмисекундный долг после загрузки. Теперь
  используется один минимальный шаг `1` за подходящий кадр вместо шести шагов
  по `10`. Лимит перекрытия снижен до 500 мкс, а порог занятого кадра — до 9 мс.
- Параметры Lua GC `pause=125` и `stepmul=100` устанавливаются при загрузке
  уровня. Это начинает следующую сборку раньше и распределяет работу ровнее,
  не вынося единственную Lua VM в небезопасный параллельный поток.
- Полный post-load `collectgarbage()` и `jit.flush()` теперь подавляются самим
  движком в течение 12 секунд после готовности мира. Исправление работает даже
  если MO2 не активировал отдельный Lua-патч.
- Scheduler проверяет уже существующий временной бюджет после каждого объекта,
  а не после группы из восьми. Пакет обычного игрового кадра возвращён с 256 на
  128; частота и содержание обновлений не изменены, остаток переносится дальше.
- Каждая задача `seqParallel` получила имя. При включённом профилировании лог
  сообщает самый долгий модуль (`alife.update`, `ai.level_path`, bullets и т. д.)
  и самый долгий scheduled-объект. Это даст точную цель для следующего патча,
  если после v74 останется другой источник тика.
- В DetailManager адаптирована безопасная микрооптимизация IX-Ray: ссылки на
  списки слотов кэшируются в горячем цикле травы. Результат рендера не меняется.

## Активный профиль

```text
lua_parallel_gc 1
lua_parallel_gc_adaptive 1
lua_parallel_gc_budget_us 500
lua_parallel_gc_call_amount 1
lua_parallel_gc_debug 0
lua_parallel_gc_frame_budget_us 9000
lua_parallel_gc_pause 125
lua_parallel_gc_postload_delay_ms 0
lua_parallel_gc_stepmul 100
lua_parallel_gcstep 1
scheduler_batch_size 128
```

## Как проверить

Загрузить то же сохранение и пройти тем же маршрутом не менее двух минут.
В логе должны появиться строки:

```text
* [Lua GC] incremental profile pause=125 ... stepmul=100 ...
* [lua-maintenance] suppressed redundant post-load full collection
* [lua-maintenance] retained post-load LuaJIT traces
* [mt-frame/profile] seqParallel slowest=...
* [mt-frame/profile] scheduler slowest=...
```

Проверять нужно по frametime и 1% low, а не только по верхнему значению FPS.
Если тик останется, две последние строки покажут его конкретного владельца.
